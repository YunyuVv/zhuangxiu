# 记录规范

## 记录原则

记录要能回答六个问题：要做什么、为什么、改了哪里、如何验证、还剩什么、下一位从哪里继续。只复制聊天或只写“已完成”无法支持接手。

| 资料 | 维护方式 |
| --- | --- |
| 项目概览 | 定位、范围、架构变化时更新 |
| 当前状态 | 有实现/验证/发布进度变化时覆盖为最新快照，保留日期及基线 |
| 任务与问题台账 | 一项一编号，更新状态与证据链接，不删除未解决事项 |
| 开发记录 | 每次实质开发/排障/部署结束时新增；同次进行中可补充，历史结论变更应注明更正日期并关联新记录 |
| 决策记录 | 重要选型、行为语义、范围变化或被否定方案单独记，说明理由与影响 |
| PRD/设计/环境文档 | 需求、接口、结构、启动/部署方式改变时同步对应段落 |

目录不按 Agent 名称分组：同一个需求可能由多个 Agent 接力，按事项和时间追踪更容易。大段原始日志按需保存脱敏片段，保留路径/链接，不把全部会话塞进交接文档。

## 编号与命名

- 任务：`T-001` 起；Bug/隐患：`B-001` 起；决策：`D-001` 起。编号永久保留，不因关闭而复用。
- 开发记录：`开发记录/YYYY-MM-DD-NN-简述.md`，同一天用序号区分，时间默认 Asia/Shanghai。
- 需单独展开的 Bug：在 `问题记录/` 新增 `B-XXX-简述.md`；重要决策放 `决策记录/D-XXX-简述.md`，有需要再创建目录。
- 小改动和简短 Bug 可直接在开发记录写清证据并由台账链接，不为每个细节额外建文档。
- 文档内引用使用仓库内相对路径；代码用路径+类/方法名，必要时附提交及行号。不要依赖只在某个聊天或某台电脑存在的链接。

## 状态定义

任务：`待办 → 进行中 → 已实现 → 已验证 → 已发布`。有真实阻塞时写明依赖条件；不涉及发布的文档任务可在已验证结束。

Bug：`待复现 → 已定位 → 修复中 → 已修复待回归 → 已关闭`；若确认是预期行为或不处理，记录理由后使用“非问题/暂不处理”。静态发现不能自动当成线上已发生事故。

- 已实现：对应代码落地，仍可能缺少联调。
- 已验证：验收条件已执行，记录环境、命令/步骤、实际结果；编译通过仅是编译层证据。
- 已发布：记录部署环境、版本/镜像、执行时间和发布后验证，不是仅完成提交或镜像构建。
- 已关闭 Bug：原复现步骤通过，相关回归完成；若只定位原因而未修复，不能关闭。

## 每次工作的流程

### 开始前

1. 读取入口、当前状态、台账与相关记录；核对最新用户指令和需求。
2. 查看 Git 的分支、HEAD、暂存/未暂存/未跟踪改动，识别哪些是已有工作。
3. 确定任务编号和最小验收条件；新需求先在台账建项。
4. 定位相关调用链和环境。文档与源码冲突时，记录差异；用户目标存在歧义时再澄清。

### 执行中

记录关键发现、失败尝试、排除依据和新的决策。Bug 必须区分观察事实、推测、已证实根因。跨天或暂停时写清当前停在哪、下条可执行动作以及需要补充的数据。

### 结束前

1. 按 [开发记录模板](模板/开发记录模板.md) 新增本次记录；Bug 可用 [Bug 模板](模板/Bug记录模板.md)，决策可用 [决策模板](模板/决策记录模板.md)。
2. 同步台账状态、当前状态中的相关模块/验证；有接口或环境变化时同步其文档。
3. 记录实际命令、退出结果、业务验证样例、未执行项与原因。失败的检查也必须保留。
4. 填写提交号；尚未提交就写“未提交，工作区状态”，不要编造提交。新记录随相关代码提交，能一起 clone 才能跨 Agent 接手。
5. 复核本次差异，保留他人改动，排除密钥和不必要构建产物；按用户当次授权处理提交/发布。

本规则靠根目录 `AGENTS.md` 提供入口，但不能保证任意第三方 Agent 自动遵循。下次委托时附入口提示词，并在任务结束检查是否更新记录。
