# 装修记录网站 · 产品需求文档（PRD）

> 版本：v0.1（草案）  |  日期：2026-08-17  |  状态：PRD 初稿，待评审
> 关联文档：`技术设计文档.md`
> 编写原则：需求描述遵循 **EARS 原则**（Ubiquitous / Event-driven / Unwanted / State-driven / Optional）；范围以 **MVP（P0）** 为主，P1/P2 标注为后续迭代。

---

## 1. 背景

装修是一个周期长（通常 2~6 个月）、参与方多、花费大、资料杂的过程。业主普遍面临四类痛点：

1. **花费失控**：零散支出记不住，月底/完工才发现超预算。
2. **资料散落**：合同、发票、品牌型号、保修单分散在微信、相册、纸质，售后时找不到。
3. **进度不透明**：各工序（拆改→水电→……→验收）到哪了、谁延期，心里没数。
4. **验收无据**：阶段照片、沟通记录缺失，验收与扯皮时无凭证。

现有方案多是通用记账 App 或相册，缺乏"按装修工序组织、花费与阶段/资料打通"的专属工具。本产品定位为**装修从 0 到完工的全过程记录台**，把周期、花销、资料、待办集中管理。

---

## 2. 目标

### 2.1 业务目标
- 让业主用一套工具完成装修全周期记录，降低信息分散与超支风险。
- 沉淀可复用的"装修账本 + 过程档案"，售后与下次装修可查。

### 2.2 成功指标（MVP 上线后观察）
- 注册用户 30 天内新建项目率 ≥ 60%。
- 单个项目平均记录花销笔数 ≥ 15 笔。
- 核心闭环（建项目→记一笔花销→看概览）完成率 ≥ 40%。
- 概览页周活 / 项目数 比值 ≥ 1.5（说明用户持续回看）。

---

## 3. 目标用户与用户故事

### 3.1 目标用户
- **核心**：正在/即将装修的业主，个人使用（MVP）。
- **未来**：开放注册后，其他业主、设计师/工长（P2 多租户）亦可入驻。

### 3.2 用户故事（MVP）
- 作为业主，我希望**新建一个装修项目**并设总预算，以便从一开始就掌控盘子。
- 作为业主，我希望**按工序阶段记录进度并拍阶段照片**，以便清楚装修到哪了。
- 作为业主，我希望**随手记每一笔花费并归到阶段/分类**，以便不漏记。
- 作为业主，我希望**一眼看到总预算 vs 已花、各阶段花了多少**，以便及时发现超支。
- 作为业主，我希望**登录后不用每次配图床密钥就能上传照片**，以便顺手记录。

## 5. 需求描述（EARS）

### 5.1 账户体系（P0）
- **Ubiquitous**：系统应始终对用户密码进行 bcrypt 哈希存储，不得以明文保存。
- **Event-driven**：当用户提交注册信息（用户名、密码）时，系统应创建账户并返回 JWT。
- **Event-driven**：当用户使用正确凭证登录时，系统应签发 JWT 并设置合理有效期。
- **Unwanted**：若用户名已存在，则系统应拒绝注册并返回"用户名已存在"提示。
- **Unwanted**：若凭证错误，则系统应返回"用户名或密码错误"且不签发令牌。
- **State-driven**：当用户未携带有效 JWT 访问受保护接口时，系统应返回 401 并要求重新登录。

### 5.2 项目/房屋档案（P0）
- **Ubiquitous**：系统应为每个用户隔离其项目数据，用户仅能访问自己的项目。
- **Event-driven**：当用户新建项目并填写名称、地址、总预算、开工/预计完工日时，系统应创建项目并自动初始化 8 个标准阶段（拆改、水电、泥瓦、木工、油漆、安装、软装、验收）。
- **Event-driven**：当用户编辑项目信息时，系统应更新对应字段。
- **Unwanted**：若总预算未填写或为负数，则系统应拒绝保存并提示"请填写有效预算"。
- **Optional**：Where 用户填写房屋面积/户型，系统应将其作为档案展示字段（不影响核心流程）。

### 5.3 阶段时间线（P0）
- **Ubiquitous**：系统应按 `sort_order` 固定展示 8 个标准阶段的顺序。
- **Event-driven**：当用户标记某阶段"进行中/已完成"并设置起止日期时，系统应更新该阶段状态与时间线。
- **Event-driven**：当用户为某阶段设置/修改预算金额时，系统应保存该阶段预算并刷新概览对比。
- **Event-driven**：当用户为某阶段上传照片（经 imgbb 直传后回传 URL）时，系统应将该图片关联到对应阶段。
- **State-driven**：当某阶段状态为"进行中"时，系统应在时间线高亮该阶段并展示进度。
- **Unwanted**：若用户将阶段标记为"已完成"但未填开始日期，则系统应提示"请先填写开始日期"。
- **Optional**：Where 用户自定义额外阶段，系统应允许在末尾追加阶段（P2 完善）。

### 5.4 花销记账（P0）
- **Event-driven**：当用户记录一笔花销（金额、分类、归属阶段、支付方式、日期、备注）时，系统应写入该笔记录并归属到项目与阶段。
- **Event-driven**：当用户编辑/删除某笔花销时，系统应同步更新概览缓存。
- **Unwanted**：若金额 ≤ 0 或分类为空，则系统应拒绝保存并提示。
- **Unwanted**：若关联图片上传失败，则系统应允许仅保存文字记录并标记"图片待补"。
- **State-driven**：当某阶段下累计花销超过该阶段预算（若有）时，系统应在概览中对该阶段标记"超支预警"。
- **Optional**：Where 用户为花销附加票据照片，系统应将该图片关联到该笔花销。
- **分类口径**：设计费 / 材料 / 人工 / 家具家电 / 其他（单选，必填）。

### 5.5 概览仪表盘（P0）
- **Ubiquitous**：系统应始终基于项目内所有花销实时计算"已花总额 = Σ 各笔金额"。
- **Event-driven**：当用户打开某项目概览时，系统应展示：总预算、已花、剩余、各阶段花费、分类占比、整体完成度。
- **State-driven**：当已花 > 总预算时，系统应在概览顶部红色高亮"已超支 X 元"。
- **State-driven**：当某阶段设有预算且实际花费 > 阶段预算时，系统应在该阶段标记"阶段超支"并提示超出金额。
- **Unwanted**：若项目暂无花销记录，则系统应展示空态引导"记录第一笔花费"。

### 5.6 图片上传（P0，跨模块）
- **Ubiquitous**：前端应在上传前对图片进行压缩（限制最长边与质量），以控制体积与上传耗时。
- **Event-driven**：当用户登录后首次需要上传图片时，前端应向 `/api/attachment/upload-key` 请求 imgbb API Key。
- **State-driven**：当本地已缓存 Key 且未超过 24 小时时，前端应复用该 Key，不得重复请求。
- **Event-driven**：前端持 Key 直传 imgbb 成功后，应将返回的图片 URL 回传后端并关联到对应项目/阶段/花销。
- **Unwanted**：若 imgbb 返回上传失败，则系统应提示"图片上传失败，可重试或仅保存文字"。

## 6. 流程说明

### 6.1 主流程（MVP 核心闭环）
```
注册/登录 → 新建项目(填预算/工期) → 系统初始化8阶段
   → 日常：记花销(归阶段/分类) / 推进阶段(传照片)
   → 随时：看概览(预算vs已花/超支预警)
```

### 6.2 图片上传流程
```
前端检测本地Key缓存
  ├─ 有且<24h → 直接用
  └─ 无或过期 → GET /api/attachment/upload-key → 缓存(24h)
→ 前端直传 imgbb(api.imgbb.com) → 拿到 image URL
→ POST /api/.../attachments (传 URL) → 关联项目/阶段/花销
```

## 7. 交互说明（关键页面，移动优先）

- **项目列表/首页**：卡片展示各项目名、总预算、已花、完成度进度条；右上角"新建项目"。
- **项目详情**：Tab 切换「时间线 / 记账 / 资料 / 概览」。
- **记账页**：表单（金额、分类下拉、阶段下拉、支付方式、日期、备注、传图）；提交后 Toast 反馈并更新概览。
- **时间线页**：竖向时间轴，8 阶段按序，可展开看照片与备注，点阶段可改状态/传图。
- **概览页**：顶部预算卡（已花/剩余/超支红字），下方分类占比（环形图）、各阶段花费条、完成度。

## 9. 验收标准（MVP）

1. 用户可注册、登录、退出，且 A 用户不能看到 B 用户项目。
2. 新建项目后自动生成 8 个标准阶段，顺序正确。
3. 记录一笔花销后，概览的"已花"立即更新；删除后回滚正确。
4. 已花 > 总预算时，概览明确红字超支提示。
5. 为阶段设置预算后，概览按阶段展示预算 vs 实际，阶段超支时明确标记超支金额。
6. 阶段可标记进行中/已完成，时间线状态同步。
7. 登录后图片上传可用；Key 24h 内不重复请求；上传失败可仅存文字。
8. 空项目打开概览显示引导空态，不报错。

## 10. 边界与异常场景

- **断网/弱网**：记账与图片上传失败应本地提示并可重试，不丢输入内容。
- **imgbb 不可用**：后端 Key 接口正常但上传失败 → 允许仅保存文字，图片后续补。
- **预算未设**：项目可先建无预算，概览隐藏"剩余/超支"，仅展示已花。
- **删除花销**：需二次确认；删除后阶段/概览汇总实时重算。
- **账号注销（P2）**：连带项目数据按隐私规则处理。

---

## 11. 权限与数据口径

- **权限**：MVP 单用户，所有数据归属当前登录用户；接口以 JWT 鉴权，后端按 `user_id` 强制隔离。
- **金额口径**：所有金额单位为"元"，保留两位小数；已花 = 该项目所有有效花销之和（不含已删除）。
- **阶段口径**：8 标准阶段顺序固定；完成度 = 已完成阶段数 / 总阶段数。
- **分类口径**：5 类固定枚举，必填。

## 12. 范围与排期建议

- **P0（本期）**：账户、项目档案、阶段时间线、花销记账、概览仪表盘、图片上传（imgbb）。
- **P1（下一期）**：资料/票据库、待办与提醒。
- **P2（远期）**：多人协作、数据导出、统计报表、小程序。

> 排期与资源（谁开发、何时上线）需由技术负责人确认，本 PRD 不拍板排期。

## 13. 待确认问题（已全部确认）

> 决策汇总：
> - **阶段预算**：需要 → 已升级为 P0 核心能力（见 §4 / §5.3 / §5.5 / 验收标准第 5 条）。
> - **阶段自定义**：P0 **固定 8 标准阶段**，自定义增删延后至 P2，不在 MVP 范围。
> - **图片压缩**：前端拍照**先压缩再直传 imgbb**（默认开启，见 §5.6）。
> - **账号注销**：MVP **不考虑**（不提供注销与数据删除功能，后续再议）。
>
> PRD 需求已锁定，无遗留待确认项，可进入评审与研发评审。
