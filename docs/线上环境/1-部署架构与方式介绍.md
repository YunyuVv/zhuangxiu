# 装修记录网站 · 线上部署架构介绍

本文说明「装修记录网站」在线上环境是如何被打包、构建与部署的，帮助你在动手前先建立整体认知。具体的 Linux 操作步骤见同目录 [2-Linux上Docker部署指南.md](./2-Linux上Docker部署指南.md)。

> 2026-11-09 核查补充：本文为部署设计说明，不是线上现状证明。现有前端已经包含指南 SSR；当前部署配置的差异与首次执行步骤见 [首次部署核对与执行清单](3-首次部署核对与执行清单.md)。

## 1. 整体架构

本项目是一个前后端分离的应用，线上以 **容器化** 方式运行，整体拓扑如下：

```
                        ┌─────────────────────────────────────────┐
   浏览器 / 用户        │            服务器（单台或同内网）          │
  ───────────────────► │                                           │
                       │   nginx :80（唯一对外入口）                │
                       │      │                        │            │
                       │      ▼                        ▼            │
                       │  zhuangxiu-web :3000    zhuangxiu-server :9096
                       │  (Next.js 前端)         (Spring Boot 后端)  │
                       │                                │      │     │
                       │                                ▼      ▼     │
                       │                    postgres :5432   redis :6379
                       │                    (PostgreSQL)    (缓存/会话)│
                       └─────────────────────────────────────────┘
```

- **nginx**：唯一对外暴露的端口（默认 80）。FRONTEND_DOMAIN 下按路径将 `/api/*` 转发给后端、其余请求转发给前端；BACKEND_DOMAIN 的所有请求直接转发给后端，两个域名统一在 docker/.env 配置。
- **zhuangxiu-web**：Next.js 15 前端服务（纯客户端渲染），容器内监听 3000，不直接对外。
- **zhuangxiu-server**：Spring Boot 后端，容器内监听 9096，不直接对外；连接同网络内的 PostgreSQL 与 Redis。
- **postgres**：PostgreSQL 16，业务库（Flyway 在启动时自动建表）。
- **redis**：Redis 7，用于缓存 / 会话等。

> web 与 server 均**不对外暴露端口**，所有外部流量都经过 nginx 同域分发。浏览器访问前端页面后，前端通过相对路径 `/api` 发请求，由 nginx 转发到后端，天然避免跨域问题。

## 2. 镜像从哪来（CI 自动构建）

镜像不靠人工在本地 `docker build`，而是由 **GitHub Actions** 在代码推送到 `main` 分支时**自动构建并推送**到 GitHub 容器registry（GHCR，`ghcr.io`）。仓库提供三个工作流：

| 工作流文件 | 产出镜像 | 用途 |
| --- | --- | --- |
| `.github/workflows/build-zhuangxiu-server-native-image.yml` | `zhuangxiu-server-native` | 后端 **GraalVM Native** 原生镜像（启动快、内存占用低，**默认推荐**） |
| `.github/workflows/build-zhuangxiu-server-image-jar.yml` | `zhuangxiu-server` | 后端 **JVM JAR** 镜像（兼容性最好，内存占用较高） |
| `.github/workflows/build-zhuangxiu-web-image.yml` | `zhuangxiu-web` | 前端 Next.js 镜像 |

每个镜像都构建 **amd64 + arm64** 两种架构，并合并为多架构 manifest（标签 `:latest` 与 `:sha-<commit>`），因此无论部署在 x86 服务器还是 ARM（如树莓派、部分云厂商 ARM 实例）都能直接拉取。

构建逻辑完全由仓库内的 Dockerfile 定义：

- 后端 Native：`docker/backend/Dockerfile.native`（GraalVM 25 容器内编译原生二进制 → 仅保留二进制的最小运行镜像）
- 后端 JVM：`docker/backend/Dockerfile.jvm`（Maven 编译 Spring Boot JAR → `eclipse-temurin:25-jre` 运行）
- 前端：`docker/frontend/Dockerfile`（pnpm 安装依赖 + `next build` → `node:22-alpine` 运行 `next start`）

> 提示：镜像名中的 `<owner>` 取自你的 GitHub 用户名（工作流自动小写转换）。首次部署前，请先把仓库 Fork / 推送到你自己的 GitHub，让 Actions 为你构建出 `ghcr.io/<你的用户名>/zhuangxiu-*` 镜像。具体见部署指南。

## 3. 两种部署形态

根据前端托管方式，提供两套编排文件：

### 形态 A：纯 Docker 全栈（推荐个人/小团队）

使用 `docker/docker-compose.yml`，一口气拉起 nginx + web + server + postgres + redis 五个容器。适合把整套服务都跑在同一台服务器上，域名直接解析到这台机器。

- 所有服务在一个 `zhuangxiu-network` 内部网络，互不暴露公网端口。
- 对外只有 nginx 的 80 端口。

### 形态 B：前后端分离（Cloudflare Pages + 1Panel 反代）

使用 `docker/docker-compose-server.yml`，只部署 **后端 + 数据库 + Redis**；前端单独托管在 Cloudflare Pages / Vercel / 对象存储等静态平台。

- 后端容器对外暴露 **9096** 端口，由宿主机上的 1Panel / Nginx 反代到域名（如 `api.yourdomain.com`）。
- 前端在构建时若需指定后端地址（本仓库前端使用相对 `/api`，通常无需配置，由静态托管平台的转发规则处理）。

## 4. 关键设计与约定

- **环境隔离靠 profile**：后端生产配置集中在 `application-prod-docker.yml`（profile=`prod-docker`），通过环境变量注入数据库 / Redis / JWT 密钥，不在仓库写死密码。Docker 内默认激活 `prod-docker`。
- **密钥不进仓库**：JWT 密钥、数据库密码等通过 `docker/.env`（由 `docker/.env.example` 复制而来）注入，`.env` 已被 `.gitignore` 与 `.dockerignore` 忽略。
- **数据库自动初始化**：PostgreSQL 无需预建库表，Spring Boot 启动 + Flyway 迁移会自动建库建表。
- **镜像可替换**：编排文件中的镜像地址用 `${ZHUANGXIU_SERVER_IMAGE}` / `${ZHUANGXIU_WEB_IMAGE}` 变量，可一键在「Native 镜像」与「JVM 镜像」之间切换，也可指向你自己构建的镜像。

## 5. 与本地开发的关系

| 维度 | 本地开发 | 线上部署 |
| --- | --- | --- |
| 前端 | `pnpm dev`（端口 9095），`next.config.mjs` 把 `/api` 代理到本地 9096 | 容器内 `next start`（3000），由 nginx 转发 `/api` |
| 后端 | `mvn spring-boot:run`（默认 profile，连 Neon 云库） | `prod-docker` profile，连容器内 postgres/redis |
| 数据库 | Neon（云 PostgreSQL） | 容器内自建 PostgreSQL 16 |

本地开发用 `application.yml` + `application-test.yml`，线上用 `application-prod-docker.yml`，二者互不影响。
