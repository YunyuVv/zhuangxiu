核查日期：2026-11-09。依据本地工作区配置；本次未触发 GitHub Actions、未确认 GHCR 中的镜像、未操作服务器。本文是首次部署指导，不是发布成功记录。

## 能否由 GitHub 打包 Docker 镜像

仓库已经配置 GitHub Actions 构建及推送镜像：

| 工作流 | 镜像 | 构建目标 |
| --- | --- | --- |
| `build-zhuangxiu-web-image.yml` | `ghcr.io/<owner>/zhuangxiu-web` | Next.js 前端 |
| `build-zhuangxiu-server-native-image.yml` | `ghcr.io/<owner>/zhuangxiu-server-native` | GraalVM Native 后端 |
| `build-zhuangxiu-server-image-jar.yml` | `ghcr.io/<owner>/zhuangxiu-server` | JVM 后端 |

三套文件均在 `.github/workflows/`。支持向 main 推送相关路径变更触发，也支持 Actions 页手动 Run workflow；仅改 docs 不会自动触发镜像构建。前端和 Native 分架构构建、合并 manifest，JVM 通过 Buildx/QEMU 构建 amd64/arm64。

需要先将要发布的代码提交并推送，包括本地新加的类和迁移；本地未提交/未跟踪代码不会被 GitHub 构建。工作流已声明 `packages: write`，还需仓库/组织策略允许 Actions 发布 GHCR。查看 Actions 的真实构建结果及 summary 中的镜像标签，再决定服务器拉取地址；配置文件存在不等于已有可拉取镜像。

## 推荐部署形态与数据库

后端需要 `api.example.com` 独立域名时，参见 [后端独立域名配置](4-SpringBoot后端独立域名配置.md)；可与下面的全栈形态同时使用。

首次采用同一台 Linux 服务器上的全栈 Docker Compose：

```text
浏览器 → Nginx:80 → Next.js:3000
                → /api/* → Spring Boot:9096 → PostgreSQL:5432 / Redis:6379
Next.js 指南 SSR ───────────────→ Spring Boot:9096
```

服务器只需安装 Docker Engine、Compose 插件和 Git，不需要另装 Java/Node/Maven；镜像在 GitHub 构建。云安全组/服务器防火墙放行所选入口端口，若配置 HTTPS 再放行 443。

现有全栈编排会启动服务器自己的 PostgreSQL，`prod-docker` 指向容器库，**不会默认连接本地开发使用的 Neon**。新库由 PostgreSQL 容器初始化数据库，Flyway 创建/升级表结构；Neon 现有业务数据不会自动迁移。如果目标是共用 Neon，应另行调整部署拓扑和 DB_URL，不直接套用本文的自建库方案。

## 当前必须先核对或修正的配置

以下保留首次核查问题及处理说明。后续已修正 Nginx 域名分流、Maven Native profile 与私密配置忽略规则，指南 SSR 和图床变量映射仍待处理；涉及镜像内容的修改需要提交后重新构建。

### 1. Nginx 配置中的 shell 占位符

已接入官方 Nginx 启动模板：在 docker/.env 中配置 FRONTEND_DOMAIN（默认 localhost）和 BACKEND_DOMAIN（默认 api.localhost），分别生成 Web/API 的 server_name。模板只读挂载到 /etc/nginx/templates/nginx.conf.template，启动时写入主配置；不再将含占位符的模板原样挂到主配置路径。域名修改后重建 Nginx 容器生效，无需手改域名。小程序 HTTPS 和合法域名配置见 [独立域名配置](4-SpringBoot后端独立域名配置.md)。尚未在目标服务器执行 nginx -t 或验证域名访问。

### 2. 指南 SSR 使用运行时的后端容器地址

`web/next.config.mjs` 当前通过 `env` 定义 BACKEND_URL，会使取值在 Next 构建中内联；默认 localhost 在 web 容器内不是后端。

建议移除 next.config 中的 `env: { BACKEND_URL: ... }` 配置块，保留 `guide.server.ts` 的服务端环境变量读取；随后在全栈 Compose 的 web.environment 中添加：

```yaml
BACKEND_URL: http://zhuangxiu-server:9096
```

重新构建前端镜像，验证运行时变量确实影响指南 SSR。浏览器 `/api` 由 Nginx 转发，和 SSR 取数是两条链路，不要只验证浏览器 API。

### 3. 传入图床 Key

后端使用 APP_IMGBB_API_KEY，但当前 Compose 的后端 environment 未传入它。需要图片功能时，增加：

```yaml
APP_IMGBB_API_KEY: ${APP_IMGBB_API_KEY:-}
```

并在服务器 `docker/.env` 填写真实值。只在 `.env` 写变量而没有 environment/env_file 映射，不会自动传入容器。

### 4. JVM 构建路径

已修正：native-maven-plugin 的 execution 移入 native profile，普通 package 只打 JAR；`-Pnative` 仍保留原生编译。本地 Git 源码快照补齐 3 个漏跟踪文件后，clean package 和 Spring AOT 通过，Linux 多架构镜像仍需新提交触发 CI 验证。20:54 两套后端构建的实际直接原因是 Git 缺失 PhaseCreateRequest、PhaseTask、PhaseTaskRepository；不能只改工作流后重跑旧提交。

### 5. 本地配置保护与 Redis

- 已补充 docker/.env、证书目录的 Git 忽略规则，以及 .dockerignore 的私有配置/证书排除；构建时不要将真实凭据或私钥 COPY 进镜像。
- 当前 Redis 服务未配置 requirepass；后端 REDIS_PASSWORD 应保持为空。若要设置密码，需要同时给 Redis 服务配置认证和调整 healthcheck，不能只改后端密码。
- APP_JWT_SECRET 是后端签名密钥，前端不需要持有；保持后端重建前后密钥稳定，否则现有 token 会失效。

## GitHub 首次构建

1. 保全并整理当前工作区，将本次要发布的实现和上述必要修正提交、推送到自己的 GitHub 仓库。
2. 打开 Actions，运行 `Build Zhuangxiu Web Image` 和 `Build Zhuangxiu Server Native Image`；若 JVM 路径已修正，也可用 JVM 工作流替代 Native。
3. 等待目标架构构建及 manifest 合并全部通过。若 ARM runner 在当前仓库不可用，应调整为适合服务器的架构，不能把部分失败的工作流当成完整成功。
4. 到 workflow summary/Packages 获取实际镜像地址。前端/Native 可使用 `sha-<完整commit>` 固定版本；JVM 标签格式以它自己的 summary 为准，不假设所有工作流一致。
5. 私有 GHCR 镜像需要在服务器登录。GitHub Actions 构建用 GITHUB_TOKEN；服务器拉取通常用有 `read:packages` 权限的访问凭据，按组织要求授权 SSO。

## 服务器操作（完成以上前置修正后）

以下以已有 Docker Engine + Compose v2 的 Linux 服务器为例。未安装时按服务器发行版安装 Docker Engine 和 Compose 插件；旧文档中的安装命令需要结合系统支持情况使用。

```bash
docker --version
docker compose version
uname -m

# 将地址替换为自己的仓库；私有仓库还需配置 Git 拉取权限
git clone <你的GitHub仓库地址> /opt/zhuangxiu
cd /opt/zhuangxiu/docker
cp .env.example .env
chmod 600 .env
```

在 `.env` 中填写下面的内容。占位字符串必须替换，不要原样投入使用；镜像 owner 为实际 GitHub 账号/组织的小写名称。

```dotenv
DB_NAME=zhuangxiu
DB_USERNAME=zhuangxiu
DB_PASSWORD=<独立生成的数据库密码>
REDIS_PASSWORD=
APP_JWT_SECRET=<openssl rand -hex 32生成的随机值>
APP_IMGBB_API_KEY=<自己的图床Key，需要图片功能时填写>
SPRING_PROFILES_ACTIVE=prod-docker
ZHUANGXIU_SERVER_IMAGE=ghcr.io/<owner>/zhuangxiu-server-native:sha-<构建成功的commit>
ZHUANGXIU_WEB_IMAGE=ghcr.io/<owner>/zhuangxiu-web:sha-<构建成功的commit>
NGINX_HTTP_PORT=80
FRONTEND_DOMAIN=zx.example.com
BACKEND_DOMAIN=api.example.com
TZ=Asia/Shanghai
```

随机值可用 `openssl rand -hex 32` 分别生成，不要共用数据库密码和 JWT 密钥。若 80 已被 1Panel/Nginx 占用，可改 NGINX_HTTP_PORT=8080，并通过现有网关为应用配置域名/HTTPS。

```bash
# 私有镜像才需要，交互输入凭据，避免写入命令历史
docker login ghcr.io -u <GitHub账号>

# 以下命令均在 /opt/zhuangxiu/docker 执行
docker compose --env-file .env -f docker-compose.yml config --quiet
docker compose --env-file .env -f docker-compose.yml pull
docker compose --env-file .env -f docker-compose.yml up -d
docker compose --env-file .env -f docker-compose.yml ps
docker compose --env-file .env -f docker-compose.yml logs --tail=100 zhuangxiu-server
docker compose --env-file .env -f docker-compose.yml logs --tail=100 zhuangxiu-nginx
```

不要把 `docker compose config` 的完整展开内容贴到公开日志，其中可能含密码；上面使用 --quiet 仅检查配置。

第一次创建的是新数据库，不预置用户，需通过注册页创建账号。访问 `http://服务器IP`，若入口端口为 8080 则访问 `http://服务器IP:8080`。域名解析至服务器后在网关配置 HTTPS，再用于正式访问。

## 验收与更新

依次验证 Nginx 正常启动、后端 Started、Flyway V1–V3 成功、公开指南 API、指南 SSR、注册登录、项目创建、阶段/子项、花销/概览、图片上传。页面能打开不等于接口及数据链路通过。验证业务删除/权限时参考交接台账中的 B-002/B-003。

更新前备份数据库并记录当前镜像标签/digest；将 `.env` 中镜像切换到已成功构建的新版本，再执行 pull 和 up -d。修改 `.env` 后使用 up -d 重建服务，仅 restart 不会注入新的环境值。

数据库数据保存在命名卷；普通 stop/down 保留数据，**down -v 会删除数据库卷**。不要把删除卷作为常规升级/迁移故障处理方式。Flyway 报错先检查版本、校验和与日志；需要恢复时按备份和迁移兼容性制定方案，不能仅回退镜像就假定数据库已回退。
